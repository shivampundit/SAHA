Part 1

Software Characteristics, SDLC Phases & Process Models (Direct TPSC PYQ Focus)

11 One-Liners
  • ⚡[TPSC PYQ 2025] Software is intangible, engineered (developed, not manufactured in the classical sense), and does NOT physically wear out (not prone to hardware wear and tear, though it deteriorates due to unmaintained changes; represented by the Bathtub Curve vs Idealized/Actual Software Failure Curve).
  • ⚡[TPSC PYQ 2025] Standard phases in the Software Development Life Cycle (SDLC) are: Requirement Gathering & Analysis -> System Design -> Coding (Implementation) -> Testing -> Deployment -> Maintenance.
  • ⚡[TPSC PYQ 2025] The VERY FIRST step in the SDLC is Requirement Gathering and Analysis (producing the SRS — Software Requirements Specification document).
  • ⚡[TPSC PYQ 2025] Functional Requirements specify WHAT the software system should do (input-output behaviors/services), whereas Non-Functional Requirements specify HOW WELL it performs (speed, security, reliability, scalability).
  • ⚡[TPSC PYQ 2025] The primary goal of a software engineer during the Design Phase is to create a blueprint or architecture (High-Level Design / Low-Level Design) for the software system.
  • ⚡[TPSC PYQ 2025] Major disadvantage of the classical Waterfall Model: It is rigid and linear — it is very difficult to go back to any previous stage once completed, and working software is not seen until the very end.
  • ⚡[TPSC PYQ 2025] Spiral Model (proposed by Barry Boehm) is a Risk-Driven evolutionary model combining iterative prototyping with systematic risk analysis in 4 quadrants (Objective setting, Risk assessment, Development/Testing, Planning next phase).
  • ⚡[TPSC PYQ 2025] Disadvantage of the Spiral Model: It can be expensive and complex (unsuitable for small, low-risk projects) due to frequent, expert-intensive risk analysis.
  • ⚡[TPSC PYQ 2025] Agile Model uses an iterative and incremental approach with short sprints (1–4 weeks) and continuous customer feedback.
  • ⚡[TPSC PYQ 2025] Fundamental principle of the Agile Manifesto: 'Customer collaboration over contract negotiation' and 'Working software over comprehensive documentation' (and 'Responding to change over following a plan').
  • ⚡V-Model (Verification and Validation Model) pairs each development phase directly with a corresponding testing phase: SRS <-> Acceptance Testing, HLD <-> System Testing, Detailed Design <-> Integration Testing, Coding <-> Unit Testing.
Part 2

Modularity, Cohesion, Coupling, DFD & Feasibility Analysis (Direct TPSC PYQ Focus)

8 One-Liners
  • ⚡[TPSC PYQ 2025] Modularity refers to breaking a complex software system into smaller, independent, manageable components or modules.
  • ⚡[TPSC PYQ 2025] Coupling refers to the degree of interdependence between two different software modules (Good software design always aims for LOW / LOOSE Coupling!).
  • ⚡Cohesion refers to the degree to which the elements inside a SINGLE module belong together functionally (Good software design always aims for HIGH Cohesion!).
  • ⚡Coupling Hierarchy (Best/Lowest to Worst/Highest): Data Coupling (best) -> Stamp Coupling -> Control Coupling -> External Coupling -> Common Coupling -> Content Coupling (worst).
  • ⚡Cohesion Hierarchy (Best/Highest to Worst/Lowest): Functional Cohesion (best) -> Sequential -> Communicational -> Procedural -> Temporal -> Logical -> Coincidental Cohesion (worst).
  • ⚡Data Flow Diagram (DFD): Level-0 DFD is called the Context Diagram (represents the entire system as a single process bubble interacting with external entities); DFD Balancing requires inputs/outputs of a parent bubble to match its child diagram.
  • ⚡Invalid DFD Rules: Data CANNOT flow directly between two External Entities, between two Data Stores, or between an External Entity and a Data Store without passing through a Process!
  • ⚡Feasibility Study evaluates 3 primary dimensions: Technical Feasibility (can we build it?), Economic Feasibility (Cost-Benefit Analysis / ROI / NPV), and Operational/Behavioral Feasibility (will users use it?).
Part 3

Software Testing, Maintenance, Refactoring & Estimation Metrics (Direct TPSC PYQ Focus)

11 One-Liners
  • ⚡[TPSC PYQ 2025] The main purpose of Software Testing is to execute a program to find defects and verify/validate whether the software works as per the specified requirements.
  • ⚡Verification ('Are we building the product right?') checks conformance to design specs via static reviews/inspections; Validation ('Are we building the right product?') checks dynamic software against user expectations.
  • ⚡[TPSC PYQ 2025] Black-Box Testing (Behavioral/Functional testing) tests software functionality WITHOUT any knowledge of internal code structure (techniques: Equivalence Partitioning, Boundary Value Analysis, Decision Tables).
  • ⚡White-Box Testing (Structural/Glass-Box testing) tests internal logic, branches, and paths WITH full knowledge of source code (uses Statement, Branch, and Basis Path coverage).
  • ⚡McCabe's Cyclomatic Complexity V(G) measures linearly independent paths (upper bound on unit test cases for branch coverage): V(G) = E - N + 2P = Number of Predicate (Decision) Nodes + 1 = Number of Regions.
  • ⚡Testing Levels: Unit Testing (individual modules) -> Integration Testing (Top-Down uses Stubs; Bottom-Up uses Drivers) -> System Testing -> Acceptance Testing (Alpha Testing at developer site; Beta Testing by real customers at user site).
  • ⚡Regression Testing re-runs test suites after code modifications or bug fixes to ensure existing functionality was not broken.
  • ⚡[TPSC PYQ 2025] Refactoring is the process of restructuring existing source code to improve its internal readability, structure, or maintainability WITHOUT changing its external behavior/functionality.
  • ⚡[TPSC PYQ 2025] Version Control Systems (like Git, SVN) track changes made to source code over time and allow multiple developers to manage concurrent versions/branches.
  • ⚡[TPSC PYQ 2025] Types of Software Maintenance (ISO/IEC 14764): Corrective (fixing bugs ~20%), Adaptive (adapting to new OS/platform/hardware ~25%), Perfective (adding features & enhancing performance — largest share ~50%!), and Preventive (refactoring for future maintainability ~5%).
  • ⚡Basic COCOMO Effort Formula: E = a · (KLOC)^b person-months for 3 project modes: Organic (small team, familiar), Semi-Detached (medium), and Embedded (tight hardware/RTOS constraints).
