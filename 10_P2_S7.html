Part 1

Language Processors, Compiler Phases & Lexical Analysis (TPSC PYQ Focus)

8 One-Liners
  • ⚡[TPSC PYQ 2024] An Assembler is the system program that translates Assembly Language mnemonics into Machine Language object code.
  • ⚡A Compiler translates the entire high-level source program into machine/target code at once, whereas an Interpreter translates and executes statement-by-statement without generating a standalone object file.
  • ⚡Preprocessor expands macros (#define) and header files (#include); Linker combines relocatable object modules and resolves external symbols; Loader loads the executable into main memory.
  • ⚡Correct Sequential Order of Compiler Phases: Lexical Analysis -> Syntax Analysis -> Semantic Analysis -> Intermediate Code Generation -> Machine-Independent Code Optimization -> Target Code Generation.
  • ⚡Symbol Table Manager and Error Handler interact with ALL 6 phases of the compiler.
  • ⚡Lexical Analyzer (Scanner, e.g., Lex/Flex) reads character streams, strips whitespace/comments, and groups characters into Tokens using Regular Expressions and Deterministic Finite Automata (DFA).
  • ⚡Maximal Munch Rule (Longest Match Rule): The lexical analyzer always matches the longest possible prefix that forms a valid token (e.g., `>=` is 1 token, not `>` and `=`).
  • ⚡Number of tokens in `printf("i = %d, &i = %x", i, &i);` is 10: `printf`, `(`, `"i = %d, &i = %x"`, `,`, `i`, `,`, `&`, `i`, `)`, `;` (a string literal is always a SINGLE token!).
Part 2

Syntax Analysis (Parsing: LL, LR, Ambiguity, Left Recursion)

9 One-Liners
  • ⚡Syntax Analyzer (Parser, e.g., Yacc/Bison) uses Context-Free Grammar (CFG) to verify syntax and build a Parse Tree (Concrete Syntax Tree) or Abstract Syntax Tree (AST).
  • ⚡A CFG is Ambiguous if at least one string has 2 or more distinct Parse Trees (or 2 Leftmost Derivations, or 2 Rightmost Derivations); checking if an arbitrary CFG is ambiguous is Undecidable.
  • ⚡Top-Down Parsers (Recursive Descent and Predictive LL(1)) construct a Leftmost Derivation from root to leaves and CANNOT handle Left-Recursive or non-left-factored grammars.
  • ⚡Eliminating Immediate Left Recursion: `A -> Aα | β` is rewritten as `A -> βA'` and `A' -> αA' | ε`.
  • ⚡LL(1) Grammar Condition: For every `A -> α | β`, FIRST(α) ∩ FIRST(β) = ∅, and if ε ∈ FIRST(α), then FIRST(β) ∩ FOLLOW(A) = ∅ (every LL(1) grammar is unambiguous).
  • ⚡Bottom-Up Shift-Reduce Parsers (LR parsers) construct a Rightmost Derivation in Reverse (reducing handles to start symbol S).
  • ⚡Power Hierarchy of LR Parsers (Smallest to Largest): LR(0) ⊂ SLR(1) ⊂ LALR(1) ⊂ CLR(1) (Canonical LR(1) is the most powerful deterministic bottom-up parser).
  • ⚡LALR(1) merges CLR(1) states that share identical LR(0) cores (so LALR(1) has the exact same number of states as LR(0)/SLR(1), cannot introduce Shift-Reduce conflicts, but may introduce Reduce-Reduce conflicts).
  • ⚡Operator Precedence Parser is the ONLY bottom-up parser that can parse certain ambiguous grammars (by plugging in external precedence/associativity rules), though it cannot handle unary+binary minus easily.
Part 3

Syntax-Directed Translation (SDT), Intermediate Code & Runtime Environments

7 One-Liners
  • ⚡Synthesized Attributes compute values solely from children attributes (Bottom-Up); Inherited Attributes compute values from parent and/or sibling attributes.
  • ⚡S-Attributed SDT uses ONLY synthesized attributes (evaluated bottom-up during LR reduction); L-Attributed SDT allows synthesized + inherited attributes from parent or LEFT siblings only (S-Attributed ⊂ L-Attributed).
  • ⚡Semantic Analysis performs Type Checking, Type Coercion (e.g., `inttofloat`), and scope verification using decorated parse trees.
  • ⚡Intermediate Representations (IR): Abstract Syntax Tree (AST), Directed Acyclic Graph (DAG — automatically merges common subexpressions), Postfix notation, and Three-Address Code (3AC: `x = y op z`).
  • ⚡3AC Implementations: Quadruples (4 fields: `op, arg1, arg2, result` — easy to move statements during optimization), Triples (`op, arg1, arg2` — uses statement indices), and Indirect Triples.
  • ⚡Runtime Memory Organization (Low to High Address): Code/Text Segment -> Static/Global Data & BSS -> Heap (grows upward via malloc/new) -> Stack (grows downward via Activation Records).
  • ⚡Activation Record (Stack Frame) contains: Actual Parameters, Return Value, Control/Dynamic Link (points to caller's frame), Access/Static Link (points to lexically enclosing scope for non-local variables), Saved Machine Status (Return PC), Local Variables, and Temporaries.
Part 4

Code Optimization & Data Flow Analysis

6 One-Liners
  • ⚡Basic Block is a maximal sequence of consecutive three-address instructions with a single entry point (the first instruction, called a Leader) and a single exit point (the last instruction) with no internal branches.
  • ⚡Leader Rules: (1) The very first instruction is a leader; (2) Any target of a conditional or unconditional jump (`goto L`) is a leader; (3) Any instruction immediately following a jump is a leader.
  • ⚡Local Optimization (within a single Basic Block using a DAG): Constant Folding (`x = 3 * 4` -> `x = 12` at compile time), Constant Propagation, Dead-Code Elimination, Algebraic Simplification (`x = x + 0` removed), and Common Subexpression Elimination (CSE).
  • ⚡Loop Optimizations (yield maximum speedup): Code Motion / Loop-Invariant Removal (hoisting expressions outside the loop), Strength Reduction (replacing expensive `i * 4` with cheaper addition `t += 4`), and Induction Variable Elimination.
  • ⚡Peephole Optimization inspects a small sliding window of target machine instructions to eliminate redundant loads/stores, unreachable code, and jumps-to-jumps.
  • ⚡Data Flow Analysis: Liveness Analysis is a Backward data-flow pass (`IN[B] = USE[B] ∪ (OUT[B] - DEF[B])`) used to build the Register Interference Graph for Chaitin's Graph-Coloring Register Allocation.

  • 📌#37 · Context-Free Grammar Why can a Top-Down Parser (such as Recursive Descent or Predictive LL(1)) NEVER directly parse a Left-Recursive grammar (`A -> Aα | β`)? → Because expanding `A -> Aα -> Aαα -> ...` causes the top-down parser to enter an infinite loop without consuming any input tokens (A leftmost expansion of `A -> Aα` repeatedly calls `A()` before matching any terminal; eliminating left recursion rewrites it as right recursion `A -> βA', A' -> αA' | ε`.)
  • 📌#38 · Top-Down Parsing What transformation prepares the grammar `S -> iEtS | iEtSeS | a` (the classic dangling-else prefix conflict) for Top-Down Predictive Parsing? → Left Factoring (`S -> iEtSS' | a` and `S' -> eS | ε`) (When two productions for `S` share a common non-empty prefix (`iEtS`), Left Factoring factors out the prefix so the parser can defer the choice until seeing the next lookahead token.)
  • 📌#39 · LL(1) Parsing In the name `LL(1)` Parser, what do the first `L`, the second `L`, and the `(1)` stand for respectively? → Scans input from Left to right, constructs a Leftmost derivation, using 1 lookahead symbol (`LL(k)`: Left-to-right scan, Leftmost derivation, `k` tokens of lookahead.)
  • 📌#40 · LL(1) Parsing In `FIRST` and `FOLLOW` set computation for LL(1) parsing, which symbol can NEVER appear inside any `FOLLOW(A)` set? → ε (epsilon / empty string) (`FOLLOW(A)` is the set of terminal symbols (plus `$`) that can appear immediately to the right of `A` in some sentential form; `ε` is never a member of `FOLLOW(A)`.)
  • 📌#41 · LL(1) Parsing Which of the following statements about `LL(1)` grammars is ALWAYS TRUE? → Every LL(1) grammar is unambiguous, free of left recursion, and left-factored (If an LL(1) parsing table has ZERO multiply-defined entries, the grammar is LL(1), which guarantees it is unambiguous and has no left recursion.)
  • 📌#42 · Bottom-Up Parsing In Bottom-Up Shift-Reduce Parsing, what derivation is constructed as the parser reduces handles back to the start symbol `S`? → Rightmost Derivation in Reverse (Right-Sentential Forms) (Each reduction replaces the rightmost handle `β` with `A`, tracing out a Rightmost Derivation in reverse (`RMDR`).)
  • 📌#43 · Bottom-Up Parsing What is a 'Handle' of a right-sentential form `γ = αβw` in Bottom-Up Shift-Reduce Parsing? → A substring `β` that matches the RHS of a production `A -> β` AND whose reduction to `A` represents one step along the reverse of a rightmost derivation (Reducing the Handle `β` to `A` is the exact inverse step of the last expansion in a rightmost derivation.)
  • 📌#44 · LR Parsing In the name `LR(k)` Parser, what do `L`, `R`, and `(k)` stand for? → Scans input from Left to right, constructs a Rightmost derivation in reverse, using k lookahead symbols (`LR(k)`: Left-to-right scan, Rightmost derivation in reverse, `k` lookahead tokens.)
  • 📌#45 · LR Parsing What is the exact strict inclusion hierarchy of Expressive Power among the four LR parser families (from WEAKEST / smallest class of grammars to STRONGEST / largest)? → LR(0) ⊂ SLR(1) ⊂ LALR(1) ⊂ CLR(1) [Canonical LR(1)] (LR(0) uses no lookahead on reductions; SLR(1) reduces on `FOLLOW(A)`; LALR(1) merges CLR(1) states with identical LR(0) cores; CLR(1) keeps full exact lookaheads and is the most powerful.)
  • 📌#46 · LR Parsing Why is `LALR(1)` (used by Yacc/Bison) preferred in practical production compilers over `CLR(1)` (Canonical LR(1))? → Because LALR(1) has the EXACT SAME (much smaller) number of states as LR(0)/SLR(1), while retaining almost all the parsing power of CLR(1) (CLR(1) tables can have thousands of states due to distinct lookahead sets; merging states with identical LR(0) cores shrinks the table by 10x to match SLR(1) state count!)
  • 📌#47 · LR Parsing When merging `CLR(1)` states that share the same `LR(0)` core to form an `LALR(1)` parser, which type of conflict can be newly introduced (and which CANNOT)? → Reduce-Reduce (R-R) conflicts CAN be introduced, but Shift-Reduce (S-R) conflicts can NEVER be newly introduced! (Shifts depend only on the LR(0) core items, so if the original CLR(1) states had no S-R conflict, merging their lookaheads cannot create an S-R conflict—only an R-R conflict.)
  • 📌#48 · Operator Precedence Which is the ONLY standard bottom-up parser that can be used (with manually specified precedence/associativity tables) on certain AMBIGUOUS expression grammars, but CANNOT handle two adjacent non-terminals? → Operator Precedence Parser (for Operator Grammars with no `ε` rules and no two adjacent non-terminals) (An Operator Grammar has no `A -> ε` productions and no right-hand side with two adjacent non-terminals (`A -> ...BC...` is forbidden).)
  • 📌#49 · SDT In Syntax-Directed Translation (SDT), what is the difference between a Synthesized Attribute and an Inherited Attribute? → A Synthesized attribute at node N is computed ONLY from attributes of N's children (and N itself); an Inherited attribute at N is computed from attributes of N's parent and/or siblings (Synthesized attributes pass information UP the parse tree (e.g., expression value `E.val`), while Inherited attributes pass context DOWN/ACROSS the tree (e.g., variable data type `T.type`).)
