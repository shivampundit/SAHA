Part 1

Cloud Computing Characteristics, Service Models & Deployment Models

6 One-Liners
  • ⚡NIST 5 Essential Characteristics of Cloud Computing: (1) On-Demand Self-Service, (2) Broad Network Access, (3) Resource Pooling (Multi-tenancy), (4) Rapid Elasticity, and (5) Measured Service (Pay-as-you-go metering).
  • ⚡IaaS (Infrastructure as a Service — AWS EC2, GCP Compute Engine, Azure VMs): Provider manages physical hardware, storage, network, and hypervisor; Customer manages OS, middleware, runtime, applications, and data.
  • ⚡PaaS (Platform as a Service — AWS Elastic Beanstalk, Google App Engine, Heroku): Provider manages up to the runtime/middleware layer; Customer manages ONLY their Application Code and Data.
  • ⚡SaaS (Software as a Service — Gmail, Microsoft 365, Salesforce, Dropbox): Provider manages the entire stack; Customer simply uses the software via a web browser/API.
  • ⚡FaaS / Serverless Computing (AWS Lambda, Cloud Functions): Event-driven execution that scales automatically to zero when idle and bills strictly per millisecond of execution.
  • ⚡Cloud Deployment Models: Public Cloud (shared multi-tenant infrastructure owned by CSP), Private Cloud (dedicated to a single organization on-prem or hosted), Hybrid Cloud (combines Private + Public with workload portability/cloud bursting), and Community Cloud (shared by organizations with common regulatory compliance, e.g., government/banking).
Part 2

Virtualization, Hypervisors, Docker Containers & Kubernetes

6 One-Liners
  • ⚡Type-1 Hypervisor (Bare-Metal / Native): Runs directly on host hardware without a host OS (e.g., VMware ESXi, Microsoft Hyper-V, Xen, KVM) — used in enterprise cloud data centres.
  • ⚡Type-2 Hypervisor (Hosted): Runs as an application on top of a conventional Host OS (e.g., Oracle VirtualBox, VMware Workstation) — higher overhead.
  • ⚡Full Virtualization vs Para-Virtualization: Full virtualization runs unmodified guest OS using hardware-assisted CPU extensions (Intel VT-x / AMD-V); Para-virtualization modifies the guest OS kernel to make direct 'hypercalls' to the hypervisor.
  • ⚡Containers (Docker, containerd) vs Virtual Machines: VMs virtualize hardware and run a full Guest OS per VM (heavy, GBs, slow boot); Containers virtualize at the OS level, sharing the Host Linux Kernel using Namespaces (isolation) and cgroups (resource limits) (lightweight, MBs, sub-second startup).
  • ⚡Kubernetes (K8s) is the industry-standard Container Orchestration platform; the smallest deployable unit in Kubernetes is a Pod (which wraps one or more tightly coupled containers sharing a single IP and storage volume).
  • ⚡Kubernetes Control Plane Components: `kube-apiserver`, `etcd` (distributed key-value store via Raft consensus), `kube-scheduler`, and `kube-controller-manager`; Worker Node runs `kubelet` and `kube-proxy`.
Part 3

Cloud Compute, Networking, Storage (Block/File/Object) & RAID

7 One-Liners
  • ⚡Horizontal Scaling (Scaling Out/In) adds or removes server instances behind a Load Balancer (high availability, cloud-native); Vertical Scaling (Scaling Up/Down) adds more CPU/RAM to a single server (hits hardware ceiling and requires reboot).
  • ⚡VPC (Virtual Private Cloud) isolates a tenant's cloud network: Public Subnets have a route to an Internet Gateway (IGW); Private Subnets reach the internet outbound-only via a NAT Gateway.
  • ⚡Security Groups (instance-level virtual firewall) are STATEFUL (return traffic is automatically allowed); Network ACLs (subnet-level firewall) are STATELESS (require explicit inbound and outbound rules).
  • ⚡Block Storage (AWS EBS, SAN — iSCSI/Fibre Channel): Raw block volumes mounted as low-latency disks for OS boot and transactional RDBMS.
  • ⚡File Storage (AWS EFS, Azure Files, NAS — NFS/SMB): Shared hierarchical POSIX directory tree mounted concurrently by multiple servers.
  • ⚡Object Storage (AWS S3, GCS, Azure Blob): Flat namespace storing objects (Data + Metadata + Unique Key ID) accessed via HTTP REST APIs (designed for 99.999999999% — 11 Nines of durability, massive unstructured data, and static websites).
  • ⚡RAID Levels: RAID 0 (Striping only, 0 fault tolerance, 100% capacity); RAID 1 (Mirroring, 50% capacity); RAID 5 (Block striping with distributed parity, min 3 disks, survives 1 disk failure); RAID 6 (Dual parity, min 4 disks, survives 2 disk failures); RAID 10 (Stripe of Mirrors, min 4 disks, high speed + high fault tolerance).
Part 4

Edge Computing, Fog Computing, CAP Theorem & Cloud Reliability

5 One-Liners
  • ⚡Edge Computing processes and analyzes time-critical data locally on or right next to the data source (IoT gateways, autonomous vehicles, 5G MEC base stations) to reduce WAN latency (to <1–5 ms) and save cloud backhaul bandwidth.
  • ⚡Edge vs Fog vs Cloud Hierarchy (Closest to Sensor -> Farthest): Mist Computing (on extreme sensor microcontrollers) -> Edge Computing (local gateways/devices) -> Fog Computing (coined by Cisco; LAN-level intermediate aggregation nodes) -> Centralized Cloud Data Centre.
  • ⚡CAP Theorem (Brewer's Theorem): In the presence of a Network Partition (P), a distributed data store must choose between strict Consistency (CP — e.g., HBase, MongoDB, Redis, Zookeeper) and Availability (AP — e.g., Cassandra, DynamoDB, CouchDB).
  • ⚡Disaster Recovery Metrics: RPO (Recovery Point Objective) = maximum acceptable age of lost data (governed by backup/replication frequency); RTO (Recovery Time Objective) = maximum acceptable downtime to restore service after an outage.
  • ⚡High Availability SLA Tiers: 99.9% ('Three Nines') = 8.76 hours downtime/year; 99.99% ('Four Nines') = 52.6 minutes/year; 99.999% ('Five Nines') = 5.26 minutes/year.
