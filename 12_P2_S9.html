Part 1

Transactions, Concurrency Problems & ACID Properties (User Example & TPSC PYQ Focus)

12 One-Liners
  • ⚡Non-repeatable read (Unrepeatable read) is a Read-Write (RW) conflict problem where a transaction reads the same row twice and gets different values because another transaction modified and committed it in between.
  • ⚡Dirty read is a Write-Read (WR) conflict problem where a transaction reads uncommitted data written by another transaction that subsequently rolls back.
  • ⚡Lost update (Blind write overwrite) is a Write-Write (WW) conflict problem where two transactions concurrently update the same data item and one overwrites the other.
  • ⚡Phantom read occurs when a transaction re-executes a range/predicate query and sees new 'phantom' rows inserted (or deleted) by another committed transaction.
  • ⚡[TPSC PYQ 2025] ACID properties stand for: Atomicity (All-or-nothing execution managed by Transaction Manager/Recovery), Consistency (Preserves database integrity constraints), Isolation (Concurrent transactions do not interfere, managed by Concurrency Control), and Durability (Committed updates survive system crashes via Write-Ahead Logging).
  • ⚡Serializable locks (Two-Phase Locking / 2PL) guarantee Conflict Serializability via a Growing Phase (acquire S/X locks only) and Shrinking Phase (release locks only), though basic 2PL is NOT deadlock-free and can suffer cascading rollbacks.
  • ⚡Strict 2PL (holds all Exclusive X-locks until Commit/Abort) and Rigorous 2PL (holds all Shared S and Exclusive X locks until Commit/Abort) guarantee Recoverability and Cascadeless schedules!
  • ⚡Conservative (Static) 2PL pre-declares and acquires all required locks before execution starts, making it completely Deadlock-Free.
  • ⚡Conflict Serializability is tested by building a Precedence (Serialization) Graph of R-W, W-R, and W-W edges: a schedule is Conflict Serializable iff its Precedence Graph is Acyclic (is a DAG).
  • ⚡Every Conflict Serializable schedule is View Serializable, and every View Serializable schedule that is NOT conflict serializable MUST contain a Blind Write.
  • ⚡SQL Isolation Levels (Weakest to Strongest): Read Uncommitted (allows Dirty, Non-repeatable, Phantom) -> Read Committed (prevents Dirty Read) -> Repeatable Read (prevents Dirty & Non-repeatable Read) -> Serializable (prevents all three).
  • ⚡Deadlock Prevention in Timestamp Ordering: Wait-Die is Non-Preemptive (Older waits for Younger; Younger dies/rolls back); Wound-Wait is Preemptive (Older wounds/preempts Younger; Younger waits for Older).
Part 2

Database Models, Keys, ER Model & Referential Integrity (Direct TPSC PYQ Focus)

10 One-Liners
  • ⚡[TPSC PYQ 2025] Main functions of a DBMS include Data Storage, Data Manipulation, Data Retrieval, and Concurrency/Security control.
  • ⚡[TPSC PYQ 2024 & 2025] Standard Database Models: Hierarchical Model (tree structure, 1:N parent-child), Network Model (graph structure where a record can have multiple parent and multiple child records), Relational Model (tables/relations), and Object-Oriented Model.
  • ⚡[TPSC PYQ 2025] Disadvantage of a Centralized Database: It creates a Single Point of Failure (and high communication bottleneck).
  • ⚡[TPSC PYQ 2025] In a Relational Database: a Table is called a Relation, a Row is called a Tuple (cardinality = number of tuples), a Column is called an Attribute (degree/arity = number of attributes), and the overall logical structure/blueprint is called the Schema.
  • ⚡[TPSC PYQ 2024 & 2025] A Primary Key is an attribute (or minimal set of attributes) that uniquely identifies each tuple/record in a table and CANNOT contain NULL values (Entity Integrity Constraint).
  • ⚡A Super Key is any set of attributes that uniquely identifies a tuple; a Candidate Key is a MINIMAL Super Key; Alternate Keys = Candidate Keys minus the Primary Key (a Candidate/Unique key CAN allow NULL unless chosen as Primary Key).
  • ⚡[TPSC PYQ 2025] A Foreign Key is an attribute in one table that references the Primary Key of another (or same) table to link two tables together.
  • ⚡[TPSC PYQ 2025] Referential Integrity ensures that every non-null Foreign Key value must match an existing valid Primary Key value in the referenced parent table.
  • ⚡[TPSC PYQ 2025] Relationships in a Relational/ER Database can be One-to-One (1:1), One-to-Many (1:N), or Many-to-Many (M:N).
  • ⚡[TPSC PYQ 2024] Natural Join Size of r1(P,Q,R) with PK=P (2000 tuples) and r2(R,S,T) with PK=R (2500 tuples): Since R is a foreign-key join referencing Primary Key R of r2, each tuple of r1 matches at most 1 tuple of r2 -> Maximum join size = 2000 (Minimum = 0).
Part 3

Functional Dependencies & Normalization (1NF, 2NF, 3NF, BCNF — Direct TPSC PYQ Focus)

8 One-Liners
  • ⚡[TPSC PYQ 2025] Normalization is the database design process of decomposing tables to remove data redundancy and eliminate Insertion, Deletion, and Update anomalies.
  • ⚡[TPSC PYQ 2024] First Normal Form (1NF) requires that every attribute contains only atomic (indivisible, single-valued) values (no multivalued or composite attributes).
  • ⚡[TPSC PYQ 2024] Second Normal Form (2NF) requires 1NF plus NO Partial Dependency (every non-prime attribute must be fully functionally dependent on the ENTIRE candidate key; a table with a single-attribute primary key in 1NF is automatically in 2NF!).
  • ⚡Third Normal Form (3NF) requires 2NF plus NO Transitive Dependency of a non-prime attribute on a candidate key (for every non-trivial X -> Y, either X is a superkey OR Y is a prime attribute).
  • ⚡Boyce-Codd Normal Form (BCNF) is stricter than 3NF: for EVERY non-trivial functional dependency X -> Y, the determinant X MUST be a Superkey.
  • ⚡3NF Decomposition is ALWAYS both Lossless-Join and Dependency-Preserving; BCNF Decomposition is ALWAYS Lossless-Join, but is NOT always Dependency-Preserving.
  • ⚡Fourth Normal Form (4NF) eliminates non-trivial Multi-Valued Dependencies (X ->> Y); Fifth Normal Form (5NF / PJNF) eliminates Join Dependencies.
  • ⚡[TPSC PYQ 2024] In R(A,B,C,D,E,F,G,H) with FDs {CH->G, A->BC, B->CFH, E->A, F->EG}, candidate keys are AD, BD, ED, FD (since D is not on any RHS); partial dependencies like A->BC violate 2NF, so R is in 1NF but NOT in 2NF.
Part 4

SQL Commands, Indexing (B/B+ Trees), Triggers & PL/SQL (Direct TPSC PYQ Focus)

9 One-Liners
  • ⚡[TPSC PYQ 2025] SQL stands for Structured Query Language; standard SQL command categories are DDL, DML, DCL, TCL, and DQL ('Data Extraction Language / DEL' is NOT a valid SQL command type).
  • ⚡[TPSC PYQ 2025] DDL (Data Definition Language) commands define/modify schema structure and auto-commit: `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `RENAME` (`CREATE TABLE table_name (col1 datatype, ...);`).
  • ⚡[TPSC PYQ 2024 & 2025] DML (Data Manipulation Language) commands manipulate table records: `SELECT` (retrieves data / DQL), `INSERT` (adds rows), `UPDATE` (modifies existing data), `DELETE` (removes rows).
  • ⚡DCL (Data Control Language): `GRANT`, `REVOKE`; TCL (Transaction Control Language): `COMMIT`, `ROLLBACK`, `SAVEPOINT`.
  • ⚡Difference between `DELETE`, `TRUNCATE`, and `DROP`: `DELETE` is DML (removes specific rows using WHERE, can be rolled back); `TRUNCATE` is DDL (removes all rows rapidly, resets storage, keeps schema); `DROP` is DDL (deletes entire table data + schema).
  • ⚡`WHERE` filters individual rows BEFORE `GROUP BY` and cannot contain aggregate functions (`COUNT, SUM, AVG, MAX, MIN`), whereas `HAVING` filters grouped rows AFTER `GROUP BY`.
  • ⚡[TPSC PYQ 2024] A Trigger is a stored statement/procedure executed automatically by the DBMS as a side effect of a database modification (`INSERT`, `UPDATE`, or `DELETE`).
  • ⚡[TPSC PYQ 2024] PL/SQL (Procedural Language / SQL) in Oracle is used to create procedural blocks, stored procedures, functions, triggers, and cursors for database operations.
  • ⚡[TPSC PYQ 2025] Database Indexing improves the speed of data retrieval (`SELECT` queries) using B-Trees or B+ Trees; in a B+ Tree, all actual data pointers reside ONLY at the leaf nodes (linked sequentially for fast range queries).
